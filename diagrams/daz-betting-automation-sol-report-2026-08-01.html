The stack is capable but not production-ready as an automated daily betting-tips service.

The main limitation is not missing modelling code. It is that data acquisition, candidate generation, Jarvis rules, the canonical ledger, Telegram delivery, scheduling and settlement do not yet operate as one evidenced, replayable contract.

Jarvis as the betting brain

Recommended role

Jarvis should be a versioned rules-and-critique service around deterministic candidates.

For each run it should:

  1. Load only active rules for the sport, market family and bet type.
  2. Load recent, approved lessons and relevant post-mortems.
  3. Receive atomic candidates with stored probabilities and quote evidence.
  4. Identify conflicts, missing evidence, stale assumptions and filler legs.
  5. Return schema-valid BET, WATCH or PASS decisions with rule IDs and vetoes.
  6. Explain accepted and rejected candidates for the operator.
  7. Propose a post-settlement lesson; never ingest it automatically in v1.

Required wiki repair

Before Jarvis influences a live paper card:

  • reconcile context/betting-engine.md with the live scheduler and service state;
  • fix the invalid metadata reported by wiki.lint on the three key betting pages;
  • add effective_from, reviewed_at, supersedes and status semantics for operational rules;
  • define precedence: current explicit Danny directive > active executable policy > current sport rule > lesson > historical report;
  • freeze a rule-set digest into every DecisionRecord;
  • keep odds, line-ups, injuries and results out of the wiki unless they are timestamped evidence documents.

Rule conflict to resolve

One Jarvis knowledge record says cards require at least three legs. The higher-value operational lesson says Danny prefers an honest two-leg SGM to a three-leg card containing filler. The no-filler rule should win:

Two justified legs are valid. A third leg is allowed only if it independently passes the single-leg quality gate.

Do not make Universal Memory a runtime dependency yet. It contains no betting records, and the Jarvis wiki is already the relevant source.

SGM and multi construction

Singles first

Every leg must pass as an atomic candidate:

fresh evidence
  + stable market/selection identity
  + calibrated model probability
  + positive edge at current price
  + risk eligibility
  + explicit evidence-backed rationale

If it would not be accepted as a single, it cannot be used to decorate an SGM or multi.

SGM gates

  1. Use two or three legs by default; never force a third.
  2. Obtain the bookmaker's exact SGM price when possible.
  3. Estimate joint probability using a declared sport/market correlation method; never multiply marginal probabilities blindly.
  4. Store the correlation method, assumptions and uncertainty.
  5. Compare SGM EV with the equivalent singles.
  6. Apply Tika Veto: odds at or below 1.15 without a data-backed reason are rejected unless Danny explicitly accepts filler risk.
  7. Reject duplicate, mutually exclusive or identity-ambiguous legs.
  8. Cap per-event, per-market and total daily exposure.
  9. Output PASS when joint probability or exact price is unsupported.

Cross-event multis

  • Build only from independently accepted singles.
  • Keep a separate product/performance segment.
  • Limit leg count and correlated exposure.
  • Retain every underlying single's evidence and model values.
  • Never use a multiplier target as a selection criterion.

Daily operating loop

Recommended cadence

For NRL, use event-relative execution rather than one stale morning price:

  1. Morning discovery: identify the decision window and generate a preview/no-bet report.
  2. Pre-decision refresh: refresh quotes/context inside a configured freshness window before the card is final.
  3. Delivery: publish one idempotent final paper card.
  4. Pre-kickoff validation: report material price/line-up changes; do not silently replace the logged tip.
  5. Nightly settlement: settle completed events and surface unresolved records.

The existing 30-minute matchday timer can remain a trigger, but it must consume a real schedule manifest and stable run IDs. The disabled general daily timer must not be enabled until dry-run acceptance passes.

Telegram card

Each message should contain:

  • run ID and generation time;
  • sport, events and coverage window;
  • source freshness/completeness;
  • accepted singles;
  • optional SGM and cross-event multi section;
  • fair odds, current odds, edge and stake tier;
  • concise evidence-backed rationale;
  • explicit vetoes/rejections and no-bet result when applicable;
  • paper ledger IDs;
  • previous settlement summary;
  • warnings and degraded dependencies.

Telegram is a delivery surface, not the ledger or placement proof.
